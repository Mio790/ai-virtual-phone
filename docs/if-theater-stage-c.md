## 本次实现及必要修正

1. 当前存档／分支的专属记忆可查看、编辑、保存。成功写入后才更新界面；保存失败保留编辑文本。每轮 Prompt 继续完整注入记忆、世界原文、主控规则、角色基础快照与落地身份。不自动总结、不压缩、不读取现代经历、不写现代记忆。分支创建继承当时记忆，随后修改相互独立。
2. IF 数据明确登记到现有“创作玩法”备份模块（追加数据源，不改变既有源下标）。完整 ZIP 备份包含剧本、角色 characterId/快照、多存档、分支、Swipes 族、当前选中分支、专属记忆及回复检查点。
3. 实际复现：IF 使用事务直写数据库，但同步 KV 缓存在水合或导入后可能仍保留旧值；原备份导出先读数据库、再用缓存覆盖，可能回退新 IF 剧情。新增仅 IF 数据源使用的 databaseOnly，导出以实际落盘值为准。其他源仍沿用原行为。
4. IF 导入按键进入专属事务路径，不经过会先更新内存的通用 KV 写入。默认跳过已有记录；覆盖须选择备份界面的明确覆盖选项。读取、恢复验证完整结构和版本分支引用；损坏时明确报错，不清空或补造数据。兼容旧备份把 IF 放在 cache 模块的形式。
   导入主记录递增本地 revision，使导入前的旧请求不能覆盖恢复结果。检查点恢复仅在完整数据内容一致（仅 revision 不同）时重新绑定到当前修订；有任何剧本、历史、分支或记忆差异都拒绝，不自动合并。
5. 检查点不再每次增量序列化所有剧本/存档：一次写入不可变请求历史快照，后续写入小型累计回复，事务读回校验。无 schema/version 变化；仍是现有 AiPhoneKvDB v1 / entries 中的 IF 专属键。兼容阶段 B 单行检查点。完成后仅移除本请求自己的检查点。
6. Stop、断流、写入失败与模拟关页：保留已落盘回复及原历史；恢复不调用 API。并发 revision 冲突拒绝覆盖。配额不足时提示复制屏幕文本，不能承诺尚未落盘的最后增量在系统强杀后存在。

## 性能与数据保留

合成 1,000 条历史、长世界原文和长专属记忆，流入 1,000 个增量：历史快照约 1,255,991 字符只写一次，累计增量写入约 2,513,511 字符，Node/fake IndexedDB 测试约 200–300ms（每次环境有波动）。断言完整世界、最后一条历史、落地身份及完整记忆仍在 Prompt 中；没有静默裁剪。

这不是 iPhone 磁盘/帧率基准。当前仍需完整历史进入内存及 Prompt，主记录每轮完整落盘，累计回复检查点仍随回复变长；极长历史的 DOM 渲染、Safari 内存、磁盘配额和后台杀页风险尚待实机测量，不宣称已解决无限长对话性能问题。
